> 后期继续补充
## 进GitHub网站为什么要加速器
- 因为它的服务器、配套资源在海外，国内直连这条跨境链路容易慢、不稳；
- 加速器本质就是换一条更好的通路。
- DNS，子域名解析不稳定

## 两种提交方式的对比
- 刚刚是直接在网页上点按钮新建文件提交,另外一种是 Git Bash 本地命令提交。
- 想法：网页上手快、适合少量文件临时补内容，但是大量修改、经常改东西的时候，命令行更方便。网页操作没法看到完整修改记录，本地 Git 可以一步步回看每一次改动。以后正式写项目，一般都用本地 Git，网页只用来应急。
 
## 文件管理的想法
- 这次踩了放错仓库、文件名带空格的坑。
- 延伸想法：仓库其实就是一套规范管理文件的办法。不是随便建文档，命名、放哪里都要有规矩。以后项目大了，文件几十个，如果乱放、名字随便写，自己和别人都看不懂。可以养成习惯：统一用短横线命名、分类放文件夹、根目录放 README 当目录。

## 版本控制到底能干啥
- 这次只是提交一次作业，然后除了交作业还能干啥
- 延伸想法：Git 不只是用来上传文件交作业。它可以保存每一次修改，万一后面改错写坏了，可以回到上一个没问题的版本。多人一起合作写东西的时候，大家各自修改，再合并到一起，不会互相覆盖文件。
 
## 索引 README 的价值
- 延伸想法：README 是给看仓库的人一份说明书。别人点开仓库，不用挨个翻文件夹，看 README 就知道这里面有什么、怎么看。以后自己写小项目，README 要写清楚：这个项目是干嘛的、怎么运行、文件结构是什么，不只是放几个跳转链接。

## 版本控制到底解决了什么老问题
- 以前写作业，我们经常复制文件：笔记v1、笔记v2、最终版、最终版真的不改了。文件一堆，分不清哪个是对的，改错了回不去。Git 本质就是帮我们告别这种手动备份。它不是单纯上传文件，而是记录每一次变更。
​
## 冲突不是bug，是协作常见的现象
之前遇到合并冲突，第一反应是“坏了、出错了”。现在想一想：两个人同时改同一个地方，程序不知道该保留谁的内容，冲突是合理的。冲突提醒我们：协作要有沟通，不能闷头同时改同一处内容；同时也说明版本工具给了我们人工审核、取舍的机会，而不是直接覆盖别人的内容。
​
## 索引的意义，不只是方便找文件
- 一开始我以为索引就是放几个链接凑目录。现在理解：索引是给阅读者（包括以后的自己）设计的导航。项目内容多了之后，如果没有索引，别人要翻一堆文件，根本看不懂结构。写索引，是在训练“结构化整理”的习惯，以后做项目、写文档都要用这个思维。
